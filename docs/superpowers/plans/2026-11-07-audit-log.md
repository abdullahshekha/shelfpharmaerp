# Audit Log Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Record every create/edit/delete on every table (plus logins) automatically, and let an Admin read the trail per order and on an Audit Log page.

**Architecture:** A Prisma client extension in `lib/prisma.ts` wraps all write operations, reads the row first for update/delete, and inserts an `AuditLog` row in the same transaction as the business write. The acting user is forwarded from `middleware.ts` (which already verifies the cookie) in an internal request header and read inside the extension via `next/headers`. Pure helpers (diff, redaction, exclusion rules, actor encoding) live in `lib/audit/` and are unit-tested; the extension and its transaction behaviour are proved by an integration QA script.

**Tech Stack:** Next.js 14.2 App Router, Prisma 7 (`@prisma/adapter-pg`), Postgres on Supabase, `node:test` via `npx tsx --test`.

**Spec:** `docs/superpowers/specs/2026-11-07-audit-log-design.md` (read its "Calls made after the builder review" section too).

## Global Constraints

- Production database, no staging: schema change is purely additive (one new `AuditLog` table). Test records are `QA `-prefixed and removed in `finally`; the QA script must also remove the `AuditLog` rows it created.
- Audit insert is in the same transaction as the business write; if the audit insert fails, the business write fails.
- Never logged / always `"[hidden]"`: `Employee.passwordHash`, `Retailer.portalPasswordHash` (scan `prisma/schema.prisma` for any other secret-like column and add it to the list).
- Never audited: the `AuditLog` table, `JournalLine`, `Notification`, and auto-posted `JournalEntry` rows (`isManual = false`). Manual journals and opening-balance entries are audited.
- Updates that only touch `Retailer.portalFailedAttempts` / `portalLockedUntil` / `portalLastLoginAt` are not audited (logins are logged as events).
- Bulk operations (`createMany`, `updateMany`, `deleteMany`) produce one entry (`BULK_*`) with a count and affected ids.
- Admin-only: both read endpoints return 403 for any role other than `ADMIN` (use `getUserFromRequest(req).role`). `env-admin` counts as ADMIN.
- Entries are append-only: the extension rejects update/delete of `AuditLog` unless `AUDIT_ALLOW_PURGE=1` (QA cleanup only).
- Reads are never logged; list pages must not get slower.
- No backfill. No retention policy.
- Dates/timezone logic elsewhere uses `Asia/Karachi`; audit timestamps are stored as UTC `DateTime` and displayed in Karachi time.

## Review Focus

1. A failing audit insert must roll back the business write, both for a plain call and inside `prisma.$transaction(async tx => …)` (test in Task 3).
2. A client-supplied `x-sp-actor` header must never become the logged actor (test in Task 2).
3. Secrets must not appear in `changes` even inside a nested create payload or a delete snapshot (test in Task 1 and Task 3).
4. `Decimal`, `Date`, `bigint` and `null` values must serialise into `changes` JSON without throwing (test in Task 1).
5. A no-op update (same values) and an `updateMany` matching zero rows must not create noise entries (test in Task 1 and Task 3).

### Task 1: Schema + pure audit helpers

**Files:**
- Modify: `prisma/schema.prisma` (add model)
- Create: `lib/audit/config.ts`, `lib/audit/diff.ts`
- Test: `tests/audit/diff.test.ts`

**Interfaces:**
- Produces (`lib/audit/config.ts`):
  - `AUDIT_EXCLUDED_MODELS: ReadonlySet<string>` = `AuditLog`, `JournalLine`, `Notification`
  - `REDACTED_FIELDS: Record<string, string[]>` (model → fields), at least `Employee: ['passwordHash']`, `Retailer: ['portalPasswordHash']`
  - `NOISE_ONLY_FIELDS: Record<string, string[]>`, `Retailer: ['portalFailedAttempts','portalLockedUntil','portalLastLoginAt']`
  - `shouldAuditModel(model: string): boolean`
  - `shouldAuditRow(model: string, row: Record<string, unknown> | null): boolean` (false for `JournalEntry` when `isManual` is not true)
- Produces (`lib/audit/diff.ts`):
  - `type FieldChange = { from: unknown; to: unknown }`
  - `toJsonSafe(v: unknown): unknown` (Decimal → string, Date → ISO string, bigint → string, nested objects/arrays recursed)
  - `redact(model: string, values: Record<string, unknown>): Record<string, unknown>` (replaces redacted fields' values with `"[hidden]"`, recursing into nested objects/arrays)
  - `diffRecords(model: string, before: Record<string, unknown> | null, after: Record<string, unknown> | null): Record<string, FieldChange>` (create: every field `{from:null,to}`; delete: every field `{from,to:null}`; update: only changed fields, compared after `toJsonSafe`; redacted fields appear as `{from:'[hidden]',to:'[hidden]'}` only if changed; `updatedAt` ignored)
  - `isNoiseOnly(model: string, changes: Record<string, FieldChange>): boolean` (true when every changed field is in `NOISE_ONLY_FIELDS[model]`)
- Produces (schema): Prisma model `AuditLog` with `id String @id @default(cuid())`, `createdAt DateTime @default(now())`, `actorType String` (EMPLOYEE | CUSTOMER | SYSTEM), `actorId String?`, `actorName String`, `actorRole String?`, `model String`, `recordId String?`, `action String` (CREATE | UPDATE | DELETE | BULK_CREATE | BULK_UPDATE | BULK_DELETE | LOGIN | LOGIN_FAILED), `changes Json?`, `reason String?`, indexes `@@index([model, recordId])`, `@@index([createdAt])`, `@@index([actorId])`.

- [ ] **Step 1: Write failing tests** in `tests/audit/diff.test.ts`: `diffRecords('Order', {status:'PENDING',updatedAt:d1}, {status:'CONFIRMED',updatedAt:d2})` equals `{status:{from:'PENDING',to:'CONFIRMED'}}`; create/delete shapes; unchanged values → `{}`; `Decimal('10.50')` vs `Decimal('10.5')` treated as equal; `redact('Employee',{name:'A',passwordHash:'x'})` → `passwordHash === '[hidden]'`; redaction reaches `{items:{create:[{passwordHash:'x'}]}}` nested; `toJsonSafe(10n)` is `'10'` and `JSON.stringify` of a Decimal/Date/bigint mix does not throw; `isNoiseOnly('Retailer', {portalFailedAttempts:{from:0,to:1}})` true, with `name` added false; `shouldAuditRow('JournalEntry',{isManual:false})` false, `{isManual:true}` true; `shouldAuditModel('JournalLine')` false.
- [ ] **Step 2: Run** `npx tsx --test tests/audit/diff.test.ts` — expect FAIL (modules missing).
- [ ] **Step 3: Implement** `lib/audit/config.ts` and `lib/audit/diff.ts` to the signatures above. Detect Decimal via `typeof v === 'object' && typeof (v as {toFixed?:unknown}).toFixed === 'function'` or `Prisma.Decimal` instance; compare decimals numerically.
- [ ] **Step 4: Add the `AuditLog` model** to `prisma/schema.prisma`; run `npx prisma generate`; push with `npx prisma db push` (additive only; confirm the output lists only the new table and no `--accept-data-loss` prompt).

**Interfaces:**

### Task 3: Prisma extension (core, atomicity, bulk, nested, cascade)

**Files:**
- Create: `lib/audit/extension.ts`, `lib/audit/log.ts`, `tests/audit/qa-audit.ts`
- Modify: `lib/prisma.ts` (apply the extension; keep the existing `omit` config and the dev global caching)
- Test: `tests/audit/qa-audit.ts` (integration, dev server on :3100, production DB, `QA ` records)

**Interfaces:**
- Consumes: `shouldAuditModel`, `shouldAuditRow`, `diffRecords`, `redact`, `isNoiseOnly`, `toJsonSafe` (Task 1); `getCurrentActor` (Task 2).
- Produces:
  - `lib/audit/extension.ts`: `auditExtension` (a `Prisma.defineExtension` over `$allModels.$allOperations` for `create`, `createMany`, `createManyAndReturn`, `update`, `updateMany`, `upsert`, `delete`, `deleteMany`; every other operation passes through untouched).
  - `lib/audit/log.ts`: `logAuditEvent(e: { action: 'LOGIN' | 'LOGIN_FAILED'; actor?: AuditActor; model?: string; recordId?: string | null; changes?: Record<string, unknown>; reason?: string }): Promise<void>` — direct insert for event-type entries (used in Task 4).
  - `lib/prisma.ts` still exports `prisma`, now audited.

**Behaviour the implementation must satisfy** (the mechanism is the builder's call, but this task starts with a spike and a gate):
- CREATE: entry with `changes` from `diffRecords(model, null, resultRow)`; nested creates inside `args.data` appear inside this parent entry (redacted).
- UPDATE/UPSERT: read the row with the same `where` before the write; entry only if `diffRecords` is non-empty and not `isNoiseOnly`; `upsert` records CREATE or UPDATE depending on whether the row existed.
- DELETE: entry holds the old values; for models with cascading children (`Order` → `OrderItem`, `Retailer` → `DrugLicense`, others per `onDelete: Cascade` in the schema) also a snapshot of the children under `changes._cascaded`.
- Bulk: one `BULK_*` entry with `{ count, ids }` (ids capped at 500, plus `truncated: true`); zero matched rows → no entry.
- `AuditLog` update/delete throws unless `process.env.AUDIT_ALLOW_PURGE === '1'`.
- Atomicity: the business write and its audit insert commit or roll back together, for a plain call and inside an interactive `prisma.$transaction(async (tx) => …)`.
- Accounting hook transactions (5 s limit) must still pass `tests/accounting/*.test.ts`.

- [ ] **Step 1: Spike (timeboxed).** In a scratch script, prove one mechanism that inserts the audit row inside the same transaction as the write for both a plain call and an interactive transaction, with the Prisma 7 pg adapter and the pooled `connection_limit=1` URL (watch for a deadlock where the hook waits for a connection the transaction holds). Candidate mechanisms: wrap non-transactional writes in a base-client `$transaction` inside the hook and, for calls already in an interactive transaction, use the transaction-bound client Prisma exposes to the hook. **Gate:** if no mechanism gives true atomicity, STOP and report to the user with what was tried — the "change fails too" decision cannot be met as designed.
- [ ] **Step 2: Write `tests/audit/qa-audit.ts` failing checks** (each uses `QA `-prefixed rows, e.g. a `QA Audit Area`): create → one CREATE entry with new values; update one field → one UPDATE entry with exactly that field; no-op update → no entry; delete → DELETE entry with old values; `createMany` of 3 → one `BULK_CREATE` with `count: 3`; `updateMany` matching nothing → no entry; creating an `Employee` with a `passwordHash` → entry shows `[hidden]`; deleting a `QA` order with items → `_cascaded` holds the items; updating `Retailer.portalFailedAttempts` only → no entry; `prisma.auditLog.update` throws; **forced failure**: make the audit insert fail (e.g. an `actorName` that violates a constraint injected through a test-only env flag `AUDIT_TEST_FAIL=1` read by the extension) and assert the `QA` area was NOT created, in both a plain call and inside `$transaction`.
- [ ] **Step 3: Run** `npx tsx tests/audit/qa-audit.ts` with the dev server up (`npm run dev -- -p 3100`) — expect FAIL.
- [ ] **Step 4: Implement** `lib/audit/extension.ts` and `lib/audit/log.ts` per the behaviour list and chosen mechanism; wire into `lib/prisma.ts`.
- [ ] **Step 5: Run** the QA script again — expect PASS; it must delete its `QA` records and its own `AuditLog` rows (with `AUDIT_ALLOW_PURGE=1`) in `finally`, and print a final count of leftover `QA` rows (must be 0).
- [ ] **Step 6: Run** `npx tsx --test tests/accounting/*.test.ts tests/audit/*.test.ts` and `npx tsc --noEmit` — expect PASS.

### Task 4: Login events

**Files:**
- Modify: `app/api/auth/login/route.ts`, `app/api/portal/login/route.ts`
- Test: extend `tests/audit/qa-audit.ts`

**Interfaces:**
- Consumes: `logAuditEvent` (Task 3), `actorFromStaffSession`, `AuditActor` (Task 2).
- Produces: `LOGIN` / `LOGIN_FAILED` entries with `model: 'Employee'` (staff) or `'Retailer'` (portal).

Rules (from the spec): staff success → `LOGIN` with the employee actor (env-admin per `actorFromStaffSession`); staff failure for any reason (unknown user, wrong password, blocked) → `LOGIN_FAILED`, `recordId` the employee id when known else null, `changes: { username, reason: 'invalid'|'blocked' }` (never the password); portal success/failure → same with `actorType: 'CUSTOMER'` (or SYSTEM with the attempted username when unknown), including the 429 lock case (`reason: 'locked'`). Logging a login must never block a successful login if the insert itself fails — the only exception to "fails together" because there is no business write to protect.

- [ ] **Step 2: Run** the QA script — expect the new checks FAIL.
- [ ] **Step 3: Implement** the calls in both login routes (staff: all return paths; portal: success, invalid, locked).
